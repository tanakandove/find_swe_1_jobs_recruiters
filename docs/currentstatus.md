# Current Status

Last updated: 2026-09-15

## Goal
Find open new-grad SWE roles on LinkedIn (job search + feed posts from connections), check whether each company has a real history of H-1B sponsorship, and surface hackathons/meetups on Fri-Sun worth traveling to for recruiting exposure — to support the user's Fall 2026 SWE job search (target: offer by Dec 2026, driven by an H-1B/OPT timeline, not just preference).

## What's working
- **`events_scraper.py`** (new 2026-09-15) — finds hackathons (Devpost, public JSON API, in-person + nationwide) and tech meetups (Luma, per-city, 9 major hiring hubs) happening Fri/Sat/Sun, flags likely recruiting-focused ones by keyword. Both sources fetched over plain HTTP, no Playwright/login needed. **Confirmed working end-to-end** (2026-09-15: 45 Devpost hackathons + 43 Luma events = 88 rows written).
- **`job_scrapper_linkedin.py`** — scrapes LinkedIn Jobs search results, filters for new-grad/entry-level/junior signals (title keywords + numbered-level detection, e.g. "Engineer I/II" vs "III+" + experience-years parsing), hard-rejects internship titles, extracts salary, and checks real H-1B sponsorship history via `h1b_sponsorship.py`. Accepts roles overlapping 0-2 years experience (widened from 0-1 per user request). Pacing tuned conservative (real personal account, not a throwaway). **Confirmed working end-to-end against live LinkedIn** (2026-09-14/15 runs: 35 jobs scraped across 5 pages, 33 matched and written to CSV with H-1B data attached).
- **`h1b_sponsorship.py`** — loads USCIS H-1B Employer Data Hub CSVs from `data/h1b/*.csv`. Auto-detects encoding (UTF-8 or UTF-16) and delimiter (comma or tab) and matches header columns by name pattern, so it handles both known USCIS export formats (the static archive files, and the live interactive tool's export, which the user actually used — see below). Matching: exact normalized name, then prefix matching for brand-name-vs-legal-subsidiary cases (e.g. "Amazon" → aggregates all 13 `AMAZON ... INC/LLC` filing entities), then fuzzy fallback for near-miss spellings (skipped on short names to avoid false positives). **Confirmed working against the user's real downloaded data** (2026-09-14: 73,417 unique employers loaded from two real USCIS exports in ~0.6s; verified correct matches for Google, Microsoft, Amazon, Meta, and correct non-matches for fake/generic names).
- **`run_scrappers.py`** — one-command entry point. Runs the LinkedIn job-search + feed scrapers (deduped, `output/jobs_<timestamp>.csv`) and the events scraper (`output/events_<timestamp>.csv`) together — kept as one app per user preference (they run this 3-4x/week when applying). No longer depends on a Django backend (that dependency was dead/missing code, removed).
- **`login_linkedIn.py`** — interactive Playwright login, saves session cookies to `linkedin_state.json` (gitignored). **Confirmed working** (2026-09-14).

## Known gaps / not yet verified
- **`job_scrapper_linkedin_feed.py`** (scrapes feed posts from connections for hiring mentions) — written but **not yet tested against a live LinkedIn session**. DOM selectors are best-effort and will likely need adjusting on first real run.
- **Luma events (`events_scraper.py`)** — each city's discover page only exposes the ~20 chronologically-nearest events with no working pagination/date filter found. On an early-week run (e.g. Tuesday), that batch may not reach as far as the coming Friday/weekend yet, showing 0 results for a city that genuinely has weekend events — they're just past position 20. Decided tradeoff, not a bug: since the user runs this 3-4x/week, later-week runs naturally reach further into the weekend and self-correct. Confirmed in a real run: nyc/sf/boston showed 0, la/seattle/austin/chicago/dc/atlanta showed 5-8 each.
- MLH (mlh.io/mlh.com) deliberately **not** included as an events source — its listing page is fully client-side rendered with no public JSON API found; most MLH-affiliated hackathons already cross-list on Devpost anyway, so the coverage gap is likely small. Revisit if Devpost coverage turns out thin.
- Events aren't filtered to the US only — Devpost/Luma results include some international listings (e.g. Toronto, Hong Kong); the location column is left as raw text for the user to judge rather than building fragile country-detection.
- This folder is **not a git repo** — no version history/rollback safety net yet.
- Recruiter-contact finding is not built into this project. A separate, unrelated sibling project (`../find_recruiters_high_roi`) has its own recruiter-search pipeline that could be referenced later, but nothing is wired up here.

## H-1B data source note
The user downloaded from the **live interactive H-1B Employer Data Hub tool** (https://www.uscis.gov/tools/reports-and-studies/h-1b-employer-data-hub, "Crosstab View" → "Download to Excel" → CSV), not the static archive files originally documented. That export is UTF-16, tab-delimited, has different column names (e.g. `Employer (Petitioner) Name` instead of `Employer`, six approval/denial category pairs instead of two), and blanks out employer names on small-count rows (USCIS privacy suppression — those rows are correctly skipped, nothing to match on). `h1b_sponsorship.py` now auto-detects and handles either format.

## Decided (don't re-litigate)
- Real personal LinkedIn account, not a throwaway — user wants feed-post job leads from their own network.
- Conservative pacing given that (lower per-run volume, longer delays) — see code constants in `job_scrapper_linkedin.py`.
- USCIS H-1B Employer Data Hub over DOL LCA as the sponsorship data source.
- No geographic travel limit for events — user is willing to fly anywhere in the US (budget-constrained, but treating this as a worthwhile sacrifice given the H-1B timeline pressure), so `events_scraper.py` isn't restricted to a home city/radius.
- Events sources: Devpost + Luma. MLH intentionally skipped (see Known gaps). Kept as one combined app (`run_scrappers.py`) rather than a separate script, per user preference — they run it 3-4x/week when applying.
